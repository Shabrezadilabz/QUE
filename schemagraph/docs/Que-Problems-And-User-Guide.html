Part A — Real-world problems Que solves now

1. “We can’t safely stitch data across systems”

Teams have Postgres + Mongo + Excel + Databricks / Snowflake / BigQuery / Salesforce with no trusted join map. Wrong keys silently poison pipelines.

What Que does: Syncs schemas only, suggests joins with scores/evidence, and forces human Promote before those joins become job truth.

2. “Catalogs inventory; nobody ships a correct stitch job”

Catalog tools describe what exists. Data engineers still hand-write joins and hope.

What Que does: Reviewed schema + joins → frozen contract → notebook job → attested export / optional CTAS or VIEW in their warehouse — something a DE can actually use.

3. “Security won’t let AI (or a vendor) touch our lake”

CISOs block “send us the lake” for AI copilots and SaaS vendors.

What Que does: Schema-first + optional capped / scrubbed samples. Assist stays off full row dumps. That unblocks evaluation and enterprise conversation.

4. “Who changed what, and can we prove this export?”

Multi-person workspaces need accountability for diligence and compliance.

What Que does: Roles (viewer / member / admin / owner), audit log, drift alerts, and HMAC-attested exports so “this stitch was reviewed and frozen” is defensible.

5. “Schema drifts and yesterday’s joins break silently”

After upstream schema change, old joins keep shipping until someone notices in production.

What Que does: Surfaces drift after sync; policy can block export when contracts / joins are stale or unreviewed.

6. “Paste into Airflow? Then what?”

Discovery tools dump SQL into chat; ops still owns delivery.

What Que does: Hands off — signed artifacts, webhook to Airflow/Dagster, optional private runner, optional materialize in customer warehouse. Que does not become the warehouse or Airflow clone.

Do not claim yet: cleaning the data lake, hosting their warehouse, auto-accepting joins, or Que as system of record for production rows.

B.2 Sync, joins, samples, jobs, schedules

2. After sync — full data or schema?

Only schema + optional capped samples in Que’s metadata DB. Sync does not copy full tables into Que.

3. How PK/FK / joins are “proven”

Today it’s a trust ladder, not automatic truth:

  1. Declared keys / FKs from connectors when available
  2. Heuristic / AI suggestions (scores + evidence)
  3. Human Promote → accepted join

We do not require “10 matching sample rows → auto-trust.” Samples support review; Promote is the gate. Export can block on unreviewed joins if that setting is on.

4. Samples — where, how many, who sees

  • Live in Que metadata (sample_values on columns), usually ≤5 per column on sync
  • Job dry-run preview uses up to ~10 illustrative rows from those samples
  • Live validate pulls up to ~20 rows read-only from the source for that run (not stored as a Que lake)
  • Scrubbing can tokenize PII
  • Anyone with workspace access who can open schema/job UI can see what’s stored (subject to scrub settings) — not “samples never leave the source” once sync-with-samples is enabled

5. “AI clean the whole data lake”

Out of scope. Que assists schema / mapping / job drafts (HITL). Row cleaning / lake transforms belong in the customer warehouse + their orchestrator.

6. “Make a new table” with joins — where is it created?

  • Usually: SQL / dbt / JSON artifact (and optional GitHub PR) first
  • Optionally: CTAS / VIEW in the customer warehouse via materialize (confirm:true)
  • Not created as a permanent table inside Que

7. Job “produces a new table” — where is data stored / retained?

PathStorage
Dry-run / live validateLogs + tiny preview in job_runs — not a result table
Export / signed artifactFile / token download — schema/SQL/bundle, not a warehouse
MaterializeCustomer warehouse object; Que keeps metadata audit only

Que is not the system of record for result rows.

8. How do they “see validated data”?

  • Que UI: capped sample / live-validate preview on the job
  • Real table: warehouse BI / SQL against the materialized object
  • Artifact: download attested export

Not: a general Que “query the cleaned lake” API.

9. Schedule daily to “pull data from connectors”

Two different schedules:

  • Source schedule: re-introspect schema (not full ETL into Que)
  • Job schedule: re-run notebook dry_run or live validate (read-only), with retries

Not “pull all connector data into Que daily.” Warehouse refresh = materialize / external orchestrator.

10. Where does the job run?

  • Default: Que API process (in-process ticker / request)
  • Optional: private runner (customer callback) if execution target = private_runner
  • Airflow / Dagster: Que only POSTs a signed webhook; they run the DAG — Que does not host Airflow

11. How another backend accesses “cleaned / job” outputs

  • Customer warehouse (after materialize) with their own credentials
  • Signed artifact URL (download export pack)
  • Orchestrator webhook payload (ids / status / refs — not full tables)

There is no “query Que workspace for cleaned row datasets” product API.

B.3 Explicitly out of v1 product

  • Que-hosted data lake / scratch warehouse
  • Auto-accepted joins (no HITL)
  • AI “clean the lake” / bulk row mutation in Que
  • Que as system of record for production row data
  • Full Airflow clone / full VPC BYOC agent (callback MVP only)
  • Full daily ETL of all connector data into Que

Part D — Typical end-to-end journey (what a member actually does)

  1. Admin invites people; sets policy (samples/scrub/block-on-unreviewed).
  2. Admin adds connectors on Sources (Postgres, Mongo, Excel, Snowflake, Databricks, BigQuery, Salesforce…); optional sync schedule.
  3. Member clicks Sync Schema — schema (+ capped samples) land in Que metadata.
  4. Open Workspace: filter by source/confidence; review edges; Promote / Reject (or use Joins inbox + Suggest mappings).
  5. Optional: AI Chat to describe tables / draft SQL / save a job.
  6. Or STITCH SESSION / sidebar Save Changes → create job.
  7. In Jobs: edit notebook → Run Test (dry-run or live validate) → see tiny preview.
  8. Deploy: Freeze contract → Export attested pack / open dbt PR / mint signed URL — and/or Materialize VIEW/table in their warehouse.
  9. Optional: schedule job re-validate; wire Airflow webhook / private runner in Settings.
  10. Use Lineage + /verify to show the path and prove the export.
