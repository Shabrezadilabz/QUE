1. Aim, motive & north star

1.1 Aim (what we exist to do)

Remove the hardest, most tribal, most error-prone work in modern data teams: understanding how systems connect, approving those connections, and shipping trusted work into the warehouse / BI / orchestrator — without forcing the company to give a vendor custody of their data lake.

1.2 Motive (why we build Que)

  • Senior DEs are bottlenecks — keys, joins, and “how we stitch finance ↔ CRM” live in their heads.
  • Catalogs inventory; pipelines still break — knowing a table exists ≠ shipping a correct join.
  • AI is blocked by security — CISOs will not “send the lake” to a chatbot.
  • Platforms are silos — Databricks/Snowflake are excellent inside one lakehouse; real companies are multi-source.
  • Teams deserve Cursor-like leverage — analysts and junior DEs should move as fast as senior people, with guardrails.

1.3 North star (Cursor for data teams)

Become the AI copilot + workflow OS for data engineers and analytics — so connecting sources, discovering joins, building models, validating, shipping to warehouse/BI, and keeping things from drifting becomes as fluid as coding in Cursor — for the whole DE/DA team, not only senior DEs.
Cursor (software engineers) Que (data engineers + analysts) ───────────────────────────── ───────────────────────────────────── Edit code with AI assist Edit stitch / models with AI assist Human reviews before merge Human Promotes joins / freezes contracts Git is source of truth Warehouse + dbt + Airflow stay SoR IDE is not the production runtime Que is not the data lake Whole team ships faster Whole DE/DA team ships trusted data faster

Analogy discipline: Cursor accelerates writing code with review. Que must accelerate data work with Promote / freeze — a wrong join is worse than a wrong autocomplete.

2.1 Problems we solve now (buyer language)

  1. “We can’t safely stitch across systems” — schema sync + suggest + human Promote.
  2. “Catalogs inventory; nobody ships a stitch job” — freeze → notebook → attested export / materialize.
  3. “Security won’t let AI touch our lake” — schema-first + capped/scrubbed samples.
  4. “Who changed what / can we prove this export?” — roles, audit, drift, HMAC attestation.
  5. “Schema drifts and joins break silently” — drift surfaces + export blocks.
  6. “Paste into Airflow? Then what?” — signed artifacts, webhooks, private runner, customer CTAS/VIEW.

5. How to sell Que

5.1 Pain narrative (open with this)

“Our DE and analytics time dies in three places: finding keys across systems, wrong joins reaching production, and security blocking AI from the lake. Catalogs tell us what exists. Platforms store the data. Nobody owns trusted stitch → ship.”

5.2 Offer (what you sell this quarter)

  • Paid design-partner / technical POC with fixed SOW (2–3 of their sources)
  • Success = N promoted joins + 1 attested export (or materialize) + precision/recall on their golden join pairs
  • Not success = “catalog coverage %” or “replace Atlan”

5.4 Ideal first customers

  • Teams already on Databricks or Snowflake but still stitching from Postgres/Mongo/Excel/Salesforce
  • Avoid first: “100% Unity Catalog, everything already inside one platform, wants full Collibra replacement”

7. Cursor for data teams — product vision in detail

7.1 The full loop we eventually own

1. Connect sources (schema sync, health, schedules) 2. Discover relationships (AI/heuristic + evidence) 3. Human approve (Promote / Reject / mapping assist) 4. Build models / jobs (notebook, SQL, dbt draft — AI assisted) 5. Validate (dry-run samples, live validate, tests) 6. Ship (export, PR, materialize, webhook) 7. Observe drift (schema/join/contract drift alerts) 8. Fix with assist (suggested remaps, PRs, re-freeze) ↑_________________ team memory of accepted joins / mappings _______|

Today Que strongly covers 1–3 and parts of 4–7. The Cursor-level product completes 4–8 as an agentic, team-wide OS — still with HITL checkpoints, still without hosting the lake.

7.3 Non-negotiable DNA (even at Cursor scale)

  • Que is not the system of record for production rows
  • Joins that become contracts require human Promote (or explicit policy exception)
  • AI may draft; humans (or policy) gate ship
  • Delivery lands in customer warehouse / git / orchestrator
  • Schema-first defaults; samples capped/scrubbed

8. Phased build plan (how to get there)

Each phase has an honest claim unlock. Do not market the next phase’s claim until exit criteria pass.

Phase 0 Harden the wedge (now → ~1–2 quarters)

Goal: Paid POCs close reliably. Join trust is demo-proof. Ship path is boring.

Claim unlock: “Controlled paid POC for cross-source join HITL → attested export/materialize.”

Build

  • Join evidence UX on every suggested edge (signals, samples overlap, optional SQL)
  • Customer golden-set eval → printable POC report (precision/recall)
  • One-click POC pack (fixtures, migrate, verify attestation)
  • Hide billing/upgrade stubs outside DEV; polish Settings credibility
  • Audit log export, session revoke, basic rate limits
  • Snowflake query-history join mining (parity with Databricks assist)
  • Deeper dbt manifest round-trip; GitHub check with attestation fingerprint + approved join IDs
  • Live connector quality: BigQuery, Salesforce, Databricks, Snowflake hardening

Exit criteria

  • ≥3 design partners run golden-set POC with documented join quality
  • SE can demo Promote → freeze → attested artifact without apology
  • Materialize or dbt PR works on at least one customer warehouse end-to-end

Phase 1 Copilot that drafts the stitch (Cursor Step 1)

Goal: Multi-step agent proposes work; humans approve at checkpoints — like Cursor proposing an edit.

Claim unlock: “AI proposes cross-source stitch plans; humans Promote; Que drafts the job.”

Build

  • Stitch Agent: “Connect domain X (orders ↔ customers ↔ payments)” → plan → suggest joins → wait for Promote → draft notebook/dbt
  • Checkpoint UI: Accept plan / edit plan / reject step (never silent auto-ship)
  • Org join memory: accepted joins & mappings reusable across jobs/workspaces
  • Better Chat → Jobs quality (tests, assumptions, cited tables)
  • Side-by-side evidence panel while agent runs
  • Analyst-safe mode: limited skills, no credential access, read-oriented

Exit criteria

  • Agent completes a 2-source stitch to drafted job with ≥1 human checkpoint in <30 minutes in POC
  • Junior DE can Promote with evidence without senior sitting beside them

Phase 2 Workflow OS for the whole DE/DA team

Goal: Que becomes daily home for stitch → model → ship → drift — not a one-time POC tool.

Claim unlock: “Team workflow OS for trusted stitch-to-ship across sources.”

Build

  • Shared workspaces by domain / data product (orders, finance, growth)
  • Review queues: joins, mappings, contract freezes, drift fixes (Slack/Teams notify)
  • Metrics & semantic stubs: approved metrics linked to frozen contracts
  • BI handoff: create/update dbt models or warehouse views that analysts query in Looker/PowerBI/Tableau
  • Job templates library (“SCD2 dim”, “fact orders stitch”, “CRM enrich”)
  • Permissions: who can Promote vs who can only propose
  • Usage analytics: hours saved, joins promoted, exports shipped

Exit criteria

  • Paying teams use Que weekly (not only during POC)
  • Both DE and analytics roles have distinct happy paths in the same workspace

Phase 3 Full Cursor-like loop (automate the bottleneck end-to-end)

Goal: From NL intent to warehouse/BI object with continuous drift repair — still HITL at trust gates.

Claim unlock: “Cursor for data teams: intent → reviewed stitch → ship → auto-detect drift → assisted fix.”

Build

  • Natural language: “Build trusted customer 360 from SF + Postgres + Databricks” → multi-agent plan
  • Validation suite generator: uniqueness, referential checks, row-count sanity (run in customer warehouse)
  • Drift agent: schema change → impact on contracts → suggested remap PR → re-freeze
  • Private runner / BYOC agent maturity (VPC) beyond callback MVP
  • Eval harnesses for hallucination; contractual schema-only guarantees
  • Grounded answers with citations to lineage edges + owners
  • Optional auto-Promote only for low-risk joins under explicit policy (default still HITL)

Exit criteria

  • Design partners report measurable reduction in DE cycle time for new domain stitches
  • Drift-to-fix PR path used in production by ≥1 customer

Phase 4 Optional expansion — catalog / governance (only after wedge revenue)

Goal: Compete with Atlan/Collibra if strategy expands — not required for Cursor-for-data.

Claim unlock: “Catalog + governance platform” — only when built.

Build (if pursuing)

  • Connector breadth at scale; dashboards/metrics/pipelines as first-class assets
  • Business glossary; stewardship workflows; certify/expire
  • Automated multi-hop column lineage across SQL + dbt + BI
  • Policy packs, Jira/ServiceNow, steward UX mode
Do not let Phase 4 steal focus from Phases 0–3. Catalog parity is expensive and slower to monetize than the Cursor wedge.

Phase 5 Enterprise control plane (Big-4 bar)

Goal: Unattended multi-tenant SaaS sellable into heavily audited enterprises.

Build

  • SCIM 2.0; enforced SSO; CMK; fine-grained RBAC/ABAC
  • SOC 2 Type II evidence pack; pen-test; contractual SLAs
  • Multi-region / tenant isolation story; SIEM export

Final line for stakeholders:
Que’s motive is to become the Cursor-like OS for data engineering and analytics. Que’s current product is the sharp first chapter: cross-source join truth + safe AI + attested delivery into systems customers already own — especially beside Databricks and Snowflake, not instead of them.

Build order: Harden wedge → Stitch agent with HITL → Team workflow OS → Full intent→ship→drift loop → (optional) catalog/enterprise control plane.
